1. Project Overview

The Military Asset Management System (MAMS) is an enterprise web application engineered for tracking, logistics coordination, and balance accounting of critical defense equipment held across multiple military bases. The system records every purchase, inter-base transfer, personnel weapon assignment, shift return, and ammunition expenditure, ensuring every physical asset is traceable to an authenticated commanding officer with tamper-proof chronological logs.

1.1 What the system does

  • Balance Accounting: For any selected base, equipment type, and date range, the system dynamically calculates and presents the Opening Balance, active Inflows/Outflows, and Closing Balance.
  • Net Movement Breakdown: The dashboard displays an aggregated Net Movement metric. Clicking on it opens an interactive modal splitting the balance into itemized Purchases, Transfers In, and Transfers Out.
  • Inter-Base Transfers: Stock moves between military installations with atomic transactional execution (@Transactional), ensuring the source base stock deduction and destination base stock addition succeed together or roll back entirely.
  • Personnel Assignments & Returns: Weapons and tactical gear are issued to soldiers by military Service Number and Name. Shift completion triggers a return action that restores available inventory in the base armory.
  • Expenditure Logging: Consumable ammunition and ordnance expended during training exercises or border patrols are permanently deducted with operational reasons.

1.2 How balances are calculated

All balance reconciliations are computed per base and per equipment type under strict mathematical inventory consistency:

Closing Balance = Opening Balance + Purchases + Transfers In - Transfers Out - Expenditures

Net movement represents the total net change during the period: inflows (purchases and transfers in) minus outflows (transfers out). Therefore:

Closing Balance = Opening Balance + Net Movement - Expenditures

Assigning equipment to personnel does not change the closing balance, because the base still maintains custody of the asset. Assigned quantity is tracked separately from available armory stock. Expended ammunition, in contrast, permanently leaves the base's holdings.

1.3 Assumptions

  • Each military base operates as an independent inventory station with its own localized stock balances.
  • An inter-base transfer takes effect atomically upon validation. The source stock decreases and destination stock increases in the same database transaction with status COMPLETED.
  • Every protected REST endpoint requires a cryptographically signed JWT in the Authorization: Bearer header.
  • Each officer account is assigned a security clearance role and associated military installation.

1.4 Limitations

  • A transfer, assignment, or expenditure cannot exceed the available armory quantity at the base. The service layer verifies this inside the transaction and throws a rollback exception if stock is insufficient.
  • Base Commanders are constrained to manage operations strictly for their assigned installation.
  • Satellite convoy GPS hardware tracking and RFID barcode scanning are targeted for Phase II deployment.

2.1 System Architecture Flow

The system follows a three-tier decoupled architecture: browser client, Spring Boot application server, and relational database. A typical request executes through these stages:

  1. Browser Client: The React application sends HTTPS REST requests with the JWT attached in the Authorization: Bearer header.
  2. Security Filter Layer: JwtAuthenticationFilter validates the token signature and loads the user's role into SecurityContextHolder. Method-level @PreAuthorize rules verify authorization before controller entry.
  3. Business Service Layer: Controllers route requests to business services. Services validate available stock quantities and execute inventory adjustments inside @Transactional methods.
  4. Data Access Layer: Spring Data JPA repositories and Hibernate map entities to tables and execute queries over JDBC.
  5. Database Layer: Relational SQL database commits all record changes, enforces Foreign Key constraints, and updates the immutable movement ledger.

3. Data Models / Schema

The relational schema uses strict Foreign Key constraints throughout to maintain mathematical consistency and prevent orphan records:

Entity / Table Primary Attributes Key Relationships & Constraints
bases id, name, code, location, commander_name, status Represents military installations. One base has many users, inventories, and movements. Unique constraint on code and name.
users id, username, email, password, full_name, role, base_id, status Stores officer credentials and clearance roles (ADMIN, BASE_COMMANDER, LOGISTICS_OFFICER). Passwords hashed using BCrypt. FK to bases.id.
equipment_types id, name, code, category, unit_of_measure, is_expendable, description, status Master defense asset catalog. Categories: WEAPON, VEHICLE, AMMUNITION, COMMUNICATION_EQUIPMENT. Unique constraint on code.
inventories id, base_id, equipment_type_id, opening_balance, available_quantity, assigned_quantity, expended_quantity, closing_balance One row per base and equipment type (Unique Composite Key on base_id, equipment_type_id). available_quantity is stock in armory; assigned_quantity is issued to troops; closing_balance = available + assigned.
movement_ledger id, base_id, equipment_type_id, movement_type, quantity, reference_type, reference_id, remarks, created_by, timestamp Append-only immutable audit record of every asset movement (PURCHASE, TRANSFER_IN, TRANSFER_OUT, ASSIGNMENT, RETURN, EXPENDITURE). Captured with officer username and server timestamp.

Security uses Spring Security 6 with stateless JSON Web Tokens (JWT). Every protected endpoint checks the caller's clearance before execution. The table below summarizes operational permissions:

4.1 Role Descriptions

Role Operational Responsibility
ADMIN Headquarters-level administrator with complete global access across all military installations. Authorized to perform all logistical and administrative operations.
BASE_COMMANDER Commanding officer managing a specific base. Issues weapons to soldiers, processes shift returns, and logs operational ammunition expenditures.
LOGISTICS_OFFICER Handles supply depot operations, asset procurement, and inter-base transfers. Restricted from troop weapon assignments and personnel records.

4.2 Enforcement Mechanism

  • JWT Authentication Filter: JwtAuthenticationFilter extracts the Bearer token, checks cryptographic validity, and injects authenticated principal into SecurityContextHolder.
  • Declarative Method Security: REST controllers use Spring Security annotations such as @PreAuthorize("hasRole('ADMIN')") and @PreAuthorize("hasAnyRole('ADMIN', 'BASE_COMMANDER')"). Unauthorized callers receive HTTP 403 Forbidden.
  • Client-Side Navigation Guards: React <ProtectedRoute> routes unauthenticated visitors to login and dynamically adapts navigation menus according to officer clearance level.

5. API Logging & Transaction Audit Trail

Every state-changing operation writes an immutable record into the movement_ledger table inside the same transaction as the change. If an operation fails, the transaction rolls back and no audit record is committed.

Audit Dimension Information Recorded
Who The authenticated username of the military officer performing the action, extracted from the verified JWT.
What The movement type: PURCHASE, TRANSFER_IN, TRANSFER_OUT, ASSIGNMENT, RETURN, or EXPENDITURE.
Target The base installation ID, equipment type ID, and the exact quantity moved.
Reference & Context Supplier invoice number, recipient base code, soldier service number, or operational drill reason.
When Server timestamp captured automatically at transaction commit time (LocalDateTime.now()).

6. Setup Instructions

6.1 Prerequisites

  • Java Development Kit (JDK 17 or higher)
  • Apache Maven (3.8+ recommended)
  • Node.js (18.x or higher) and npm
  • MySQL 8+ or PostgreSQL 14+ (or default auto-configured H2 database)

6.2 Running the Backend

cd backend
mvn clean compile
mvn spring-boot:run

The backend REST server starts at http://localhost:8080. On initial startup, DataInitializer.java automatically sets up the relational schema and seeds default military installations and demo officer accounts.

6.3 Running the Frontend

cd frontend
npm install
npm run dev -- --port 5173

The frontend Vite development server launches at http://localhost:5173 with instant hot module replacement.
